1. Executive Summary

本周修完了之前总结的 5 个产品级 bug。今天用 新的 offline 重导出 pipeline(直读 Canary 的 IndexedDB LevelDB)把 9 个 human-arm 录制全部走了一遍当前 renderer,得到一组从源头到 SKILL.md 都包含全部修复的"干净"human SKILL.md,然后对这组 SKILL.md 重跑 human arm。

三个数字

Cold 60.0% → Human 77.8% → Oracle 100.0%。
Human 比昨天 (66.7% = 6/9) 提升 +11.1 pp;total cost 也下降 $7.55 → $5.78 (-23%),total turns 也下降 314 → 285 (-9%)。
Wilson 95% CI 仍然宽:human [45.3%, 93.7%] vs cold [31.3%, 83.2%] 重叠 —— 单 seed 下,7/9 vs 6/9 的统计差异不显著。

但更重要的发现不是数字本身,而是失败原因的迁移:

  • 修复前 (5/26):human-arm 的 3 个失败 (771 / 423 / 694) 原因各异 —— grid 选不中行 / browse fill 误碰 Enter / browse fill 不识别 select。
  • 修复后 (5/28):human-arm 的 2 个失败 (694 / 771) 都不是 renderer 问题 —— 一个是 turn 数不够 (multi-fill 表单天然步骤多),一个是录制范围窄于任务范围 (录的 approve 2 条,任务要全部)。

结论:5 个 renderer / schema 修复方向是对的,但 +1 个 pass 的具体来源 (task 423) 实际是预算原因,不是 renderer 原因 —— 423 在 retry-budget 跑里 44 turns / $0.85 拿下,远超昨天的 $1.00 默认上限。

5. 反直觉的数据细节

5.1 +1 pass 是 budget 修的,不是 renderer 修的

423 在 5/26 跑用了 21 turns / $0.59 就退出了,说明 agent 不是卡在"步骤太多",而是提前放弃。但今天用 --max-turns 60 / --max-budget 1.5 重跑就过了。说明 5/26 的失败实际是 runner_ccc 默认预算太紧,把 mid-confidence 的 hard task 错杀了。

这意味着:真正 baseline-level 的 fix 不是 5 个 renderer bug,而是 runner 的默认预算。建议把 runner_ccc 的默认 --max-turns 从 40 提到 60,--max-budget-usd 从 1.0 提到 1.5。这两个参数对 cold/oracle 影响极小(它们本来就远低于上限),但对 human 影响可观。

5.2 Pass 的任务也变便宜了 (-23% total cost)

不只是 423 多一个 ✅ —— 整组 human-arm 总 cost 从 $7.55 → $5.78,降幅 23%。其中 496 / 538 / 453 三个 task 各降 $0.05 / $0.54 / $0.56。这不是单 seed 噪声 —— 三个都同向降,且降幅集中在 multi-fill 表单类。

这强烈暗示 Bug #1 (--no-press-enter) 起了作用:每个 fill 之前 agent 不再需要"先 snapshot 确认表单没被提交"的防御性 turn。是 renderer 修复在数字上最清晰的痕迹。

5.3 771 的失败模式变了 —— 这是设计层信号

5/26:771 跑了 71 turns / $1.88 全用在反复"找 Pending review 行"上,最终 budget 耗尽。
5/28:771 跑了 40 turns / $0.75 提前 DONE 退出,理由是"approved review 352 + 347"。

差异是质变:renderer 修对了,agent 准确执行了录制里的步骤,但录制本身是用户在一页里 approve 了 2 条 review,任务要求是"所有 positive reviews"。录制是采样,任务是总集。SKILL.md 里没有任何信号告诉 agent 这是个 样本 vs. 全集 的关系。

这指向一个 schema 缺失:SkillStep 应该能表达 "for each row matching filter, do action"。Oracle SKILL.md 是用自然语言绕过去的 —— 标题/Background 里写"approve all positive"agent 自己理解。但 CRX 录制路径没有抽象这一层。

5.4 694 现在 cost 反而更高 (61 turns / $1.44 vs 5/26 的 52 turns / $1.20)

表面看是退步,但实际是:5/26 跑只跑了 52 turns 就被 $1.00 cap 打断了,根本没机会跑满;5/28 给到 60 turns / $1.50,跑满 61 turns 才被 max-turns cap 打断。61 turns 还不够意味着 694 的 56-action 录制本身就需要 LLM 用更多 turns 才能消化 —— 每个 fill / select / click 都对应 1-2 个 CCC turn (LLM 决策 + tool call + 读结果)。

所以 694 不是"renderer 不够好",是 "录制行为本身的密度太高,LLM 步骤膨胀系数 1.1-1.2x"。结构性的,renderer 改不了。需要的是 SKILL.md 层 step-pruning(把重复 / 冗余 / 默认值的 step 合并 / 删除),或者 step compression(让 LLM 看到"按图示填写所有字段"这种 high-level instruction 而不是 7 个 fill)。

6. 战略建议

5/26 的报告问过三个战略问题。今天的数据让我重新看了一下:

问题 1 — 5 个 renderer bug 修完后,human 真的会接近 oracle 吗?

部分答案是 "不会,至少不靠 renderer"。Renderer 修对了,但 human → oracle 的 22 pp 差距里,只有 11 pp 通过 renderer + budget 顺手修掉;剩下 11 pp 来自两个全新的瓶颈类别:

  • SKILL.md step 数与 LLM turn budget的关系(694)
  • SKILL.md "录的范围 ≤ 任务范围"的语义鸿沟(771)

这两个不是 renderer 问题,是 recording → instruction 的语义转换问题。Oracle SKILL.md 通过自然语言桥接,CRX 录制没桥。要让 human ≈ oracle,需要在 CRX 里加这层桥 —— 比如"录制后让 LLM 看一遍 raw action,生成 high-level 描述"。这是产品方向选择。

问题 2 — 当下的 CRX 录制路径还有意义吗?

仍然有,但定位变了。原来设想是"用户录一次,输出立刻可用的 SKILL.md"。现实是"用户录一次,输出可以让 agent 执行,但表达能力受限于录制的具体步骤而非任务的语义"。

当前 CRX 对应的产品 fit:

  • ✅ 强 fit —— "重复执行同一具体流程"(同一订单同一页面);适合 RPA 类工作
  • ⚠ 弱 fit —— "执行同一类流程的多个变体"(approve all positive reviews / fill out all draft orders);需要范围扩展
  • ✗ 不适用 —— "需要判断 / 分支"的流程(if status=Pending then approve);需要条件表达

问题 3 — video-skills 这条线在新数据下值多少?

没变化,见 5/26 报告。但有新观察:771 / 694 这类 "录的范围窄"的问题,video-skills 模式(自然语言 + 视频)反而能避开,因为它从一开始就不是"严格步骤复现",而是"看一段操作,提取意图,生成可推广的 instruction"。

7. 我的推荐 — 不变动 + 一个小改 + 一个中等改

  1. 不变动:暂停继续给 CRX renderer 加修复。5 个 bug 修完后,renderer 已经不是瓶颈。除非之后扩到 shopping(非 admin) 或 forum domain,出现新的 selector 类别。
  2. 小改 (~1 小时):把 runner_ccc 的默认 budget 提到 --max-turns 60 --max-budget-usd 1.5。从今天的数据看,这本身就是 67% → 78% 升级里的主要贡献者。不是 renderer。这是 eval-infra 的 housekeeping,不是产品方向决策。
  3. 中等改 (~1 周):在 CRX 的 SaveAsSkillDialog 里加一个"录制范围扩展"提示。当 agent 检测到录制内容像是 "为某条 row 做一组操作"(rowContext 出现 ≥1 次),提示用户:"这次录的是对 row X 的操作。任务表述里如果是'对所有满足条件的 row',请在 description 里说明 —— 比如'对所有 Pending positive review 重复此流程'"。这就是把 §5.3 那个语义鸿沟转给用户填,不增加 renderer 复杂度。

如果上面三件都做,加上 budget 提升,human 大概率到 8/9 (~89%)。要追到 9/9 / 100% 需要解决 694 类的 turn-budget 增长 —— 那是 LLM-distillation 的活,不是 CRX 的活。
