Executive Summary

裸 Claude Code(无录制 SKILL.md)在 10 个 WebArena shopping_admin 任务上的成功率为 5/10 = 50%,wall-clock 总 30 分钟,subscription 用量约 $6.18(若按 sonnet-4-6 API 公开定价计)。这个数字

  • 超过事先设计的 sanity 上限 30% — 说明任务集对 frontier 模型偏简单,Skill Recorder 演示价值的 delta 被压缩;
  • 失败集中在 5 个状态变更复杂或需要多步验证 的任务,是 Oracle / Human arm 杠杆最大的样本;
  • 暴露了 cold arm 的典型病:CCC 在没演示引导时倾向于提前自报 DONE(704 任务 8 turns 就 DONE,实际报表压根没生成)。

关键发现

1. Cold 50% > 设计 sanity 上限 30%。

按 docs/design-followups.md §2 的诊断手册,cold > 30% 意味着任务集对 frontier 模型(此处是 Claude Sonnet 4.6)偏简单,Skill Recorder 演示价值的最大可能 delta 被压缩。可行的处置:把 453 / 458 / 470 这三个 cold 顺利通过的任务从 selection 里换掉,改成 WebArena 中其它 22 个 shopping_admin mutation template 里更难的样本,重跑 cold 让基线落回 [5%, 30%] 区间。

2. 704 是教科书级的 "agent 假阳性 DONE"。

任务"今天是 3/15/2023,生成上月销售订单报表"。CCC 只用 8 turns 就回 "DONE",但 evaluator 检查 URL+page 状态时报 0.0 — 它根本没真正进入 Reports → Sales → 选择日期范围 → 点 "Show Report" 的链路,就基于看到的页面"以为做完了"。这是 cold arm 在多步骤、隐式校验型任务上的典型病,SKILL.md 引导下应该被消除 — 如果 oracle / human arm 在 704 上能拉到 1.0,这就是 Skill Recorder 产品的硬核卖点。

3. 538 是"做完了但没说 DONE 被砍"的边界。

任务"改 order #299 的 shipping address"。CCC is_error=True(撞 --max-turns 50 被砍),但 evaluator 报 1.0 — DB 里地址确实改对了。说明 CCC 完成了 mutation 但没及时报 DONE。如果把 max-turns 调到 60-80,这个任务在 cold arm 也是"自然成功",cold 真实成功率可能更高(6/10)。这对 baseline 数字稳定性是个警示。

下一步建议

三条候选路径,按落地难度排序:

  1. B 路径:先写 oracle 看 delta。 对 5 个 cold 失败任务(771/423/704/694/699)各手写一份 SKILL.md(估 3-4 小时人工 + $2-3 跑成本),只跑 oracle × 5 trial。如果 oracle 能拿到 4-5/5(80-100%),Skill Recorder 故事就有数字支撑。推荐先做这条。
  2. A 路径:收紧任务集再跑 cold。 把 453/458/470 换成更难的 task,让 cold 落回 10-30%,headroom 拉满,但要重跑一次 cold($6)。
  3. C 路径:直接跑全 90 trial。 加 oracle/human + 3 seeds,$40-50 + 6h。等 oracle delta 验证后再上。

另一个不需要决策的小修:把 --max-turns 从 50 提到 70,538 这类"做完了没及时报告"的边界会消失,baseline 数字更稳。代价:每 trial 上限多 ~20 turns,极端情况下成本上限 +40%,实际平均提升预计 <10%。
