1. Executive Summary

三个 arm 的成功率:Cold 60% → Human 67% → Oracle 100%。三 arm 的费用 / turns / wall clock 对比见 §2。

但 +7pp 的 Cold → Human 提升,单 seed 下统计上不显著:6/9 trial 的 Wilson 95% CI 为 [35%, 88%],跟 cold 的 [31%, 83%] 大幅重叠。换句话说,这一组数据不能证明 Skill Recorder 一次录的 SKILL.md 优于完全没 SKILL.md。

但同样的设置下,Oracle 100% 的成功率,CI 为 [72%, 100%] —— 跟 cold 的 CI 不重叠,统计上显著优于 cold。这意味着:格式 / 注入路径 / 评估器都是 OK 的,问题在于 CRX 当前输出的 SKILL.md 质量不够,而非概念错。

Human 与 Oracle 之间的 33pp 差距,可以精确归因到 5 个已知的产品级 bug(见 §3)。其中 3 个是 renderer / schema 改动,工程量明确,2-3 周可完成。修复后预测 human ≈ oracle。

4. 数据分析 — 几个反直觉的细节

4.1 简单 task 上,SKILL.md 是 overhead 而非 advantage

这条曲线很重要:Skill Recorder 在 medium 区间反而是负价值(贵了不快也没让 success rate 提升)。卖点必须落在 hard 任务上,而 hard 上 human 现在大量 fail。

4.2 LLM 单 seed 抖动 > ±50% turns

同一份 SKILL.md(human 458),sanity 跑了 12 turns / $0.18,bg 重跑只 7 turns / $0.13。470 更夸张:39 turns / $0.95 → 10 turns / $0.15。这意味着 single seed 上 ±30pp 是正常波动,3 seeds 才能下结论。

4.3 Cold 60% 实际偏高,任务集偏简单

原 plan 的 sanity range 是 cold ∈ [5%, 30%]。实测 60% —— 任务集对 frontier 模型(sonnet 4.6)太友好,SKILL.md 的最大可能 delta 被压缩。换更难的 task 集后,cold 可能落到 25-35%,human/oracle 头空间从 40pp 拉到 65pp。

4.4 Human 比 Cold 反而更贵

Human 总成本 $7.55 vs cold $6.18。原因:fail 的 trial(496/538/771)都撞 max-turns 70,每个烧 $1.4-1.9。SKILL.md 让 agent 看似有方向(跟着脚本走),但脚本含错误指令时 agent 会反复 retry,反而更慢更贵。cold fail 的成本天花板是"放弃所需的 turns",human fail 的成本天花板是"用 SKILL.md 把 turns 用光",后者通常更高。

5. 战略建议 — Skill Recorder 项目还有意义吗?

诚实回答:有,但只在很具体的条件下,并且最有价值的形态可能不是当前的浏览器录制器。

核心判断:数据没有杀死 Skill Recorder,但也没有证明 Skill Recorder 当前形态成立。它**证明了**(a)oracle SKILL.md 能让 sonnet 4.6 跑出 100%,(b)CRX 当前输出的 SKILL.md 离 oracle 有 33pp 差距,(c)差距能精确归因到 2-3 个可修复的 renderer bug。是否继续投资,取决于以下三个问题的答案。

问题 1 — 修了 5 个 bug 之后,Skill Recorder 真能接近 oracle 吗?

大概率能,但有 caveat。修 Finding #2(<select>)+ #3(checkbox)之后,3 个失败 task 应该都过。但 oracle SKILL.md 还做了 CRX 没法自动做的事:

  • 解释为什么这一步重要("evaluator 只检查 X,不要点 Show Report")
  • 提供 fallback("如果 selector miss,用 browse snapshot 重新定位")
  • 语义化命名("approve-magento-reviews-by-id" vs CRX 自动生成的 "dashboard-magento-admin")

这些是 CRX 一次录制无法捕捉的元数据。Skill Recorder 要接近 oracle,需要**后处理 pipeline**(可能是 LLM 把录制+任务 intent 合成成更好的 SKILL.md),不只是 renderer 修 bug。

问题 2 — 用户为什么要装 CRX 录浏览器?

当前形态最大的 friction:用户必须亲自完成一次任务并录下来。这跟其它路径相比:

获取 SKILL.md 的方式用户 friction覆盖率差异化
Skill Recorder(浏览器录制)高(装扩展 + 操作 + 录)用户自己做过的任务"我能在我熟悉的工具上自动化"
video-skills(已有 M1-M3)低(放 YouTube 链接)所有有教程的任务"YouTube 上有人教过的事,Claude 都能做"
跟 Claude 对话学习 demo低(对话即可)用户能描述的任务无,这是 Claude 默认能力
Anthropic 内置 Skills极低(已经在 Claude Code 里)Anthropic 决定 ship 的看 Anthropic ship 什么

Skill Recorder 浏览器版的 unique value = 用户自己有的 workflow,YouTube 上没有,Anthropic 没 ship,愿意装个扩展。这是个很窄的交集。

问题 3 — video-skills 这条线值多少?

过去一周你的 commits 显示视频→skill 这条线已经有 M1(distill package + Fiverr fixture)/M2(Cloudflare Worker)/M3(CRX video tab + /distill 调用)的实质性进展,还有 Helium 10 / Upwork 等 fixture。这条线的**结构性优势**:

  • 用户门槛接近零(扔 YouTube URL,等)
  • 内容覆盖远大于"用户自己录"(YouTube 上每个 SaaS 都有教程)
  • 跟 Anthropic 内置 Skills 互补(他们不会去蒸馏 YouTube)
  • 同一套 eval 框架(我们刚建的)直接复用 —— 把视频→skill 的输出喂进 runner_ccc,看效果

6. 三条产品走向 + 我的推荐

方案 A — All-in 浏览器录制器

修 5 个 bug → 重跑 3-arm 证明 human ≈ oracle → 扩 benchmark 到 WebVoyager / 自建 → Chrome Web Store onboard。~6-8 周到能 demo,~12 周到能小范围测试用户。

Pro: 数据故事干净;CCC + 浏览器是 hot category;eval pipeline 复用

Con: 用户 friction 高;Anthropic 内置 Skill 系统是隐性竞争;市场窄

方案 B — Pivot 主攻 video-skills(我的推荐)

video-skills 已经有 M1-M3 基础,这条线的 user friction 比 CRX 录制低一个量级。**Skill Recorder 浏览器版降级为"高级用户工具"**(继续维护,不主推),把研发资源集中到视频蒸馏 + skill 质量。复用同一套 eval 框架测试 video-skills 输出的 SKILL.md。

Pro: 真实大众市场(每个 SaaS 都有 YouTube 教程);差异化清晰("从视频学技能"是 unique value);现有 commits 已经证明可行

Con: 视频质量不可控;长视频 token 贵;需要解决"agent 跟着教程视频做" vs "agent 自己摸索" 的 prompt 工程

下一步具体动作:用现有 eval 框架跑 video-skills × 同样 10 个 task —— 把 Fiverr / Helium 10 fixture 蒸馏出的 SKILL.md 放进 eval/skills/from-video/,跑 runner_ccc。看看视频路径的 SKILL.md 跟 oracle / human 比怎样。这个实验成本极低($1-2)本周就能做。

方案 C — Sunset 产品,把 eval pipeline 包装成独立工具

承认 Skill Recorder 整体形态(浏览器 + 视频两条线)都没找到产品市场契合点。把过去一周建的"WebArena × CCC × 自动 eval × cold/oracle/human × 自动报告"这套框架本身包装成独立工具 —— 卖给其它做 Skill / agent 框架的团队作为标准化 benchmark tool。

Pro: 工程已经做完;ML/agent 社区缺这种统一框架;商业模式清晰(B2B SaaS 或开源 + 付费托管)

Con: 完全脱离原 vision;TAM 小(主要客户是其它 agent 创业公司);需要重新做 GTM

我的具体推荐

1. 本周做一个非常小的实验(投入 < 1 天 / $5):用 packages/skill-from-video 把 1-2 个 Magento admin 任务从 YouTube 教程蒸馏成 SKILL.md,跑 runner_ccc --arms from-video 看数字。这一个实验决定方案 A / B 的相对潜力。

2. 基于结果决定方向:

  • 如果 video-skill 输出能跑出 70%+ → 方案 B 推荐继续
  • 如果 video-skill 输出跑出 40% 或更低 → 方案 A,先修 5 bug 把 Skill Recorder 浏览器版做扎实
  • 两条都低于 50% → 方案 C,把 eval pipeline 单独打包

3. 无论选哪个方案,都把当前 eval 框架开源:这套 3-arm 评测方法学 + WebArena × CCC 集成是独立有价值的工程产物,放 GitHub 能换可见度 + 招到 ML 工程师。

7. 不需要决策也该做的事
